# Candidate tool review — source-backed desk research, 2026-11-01

**Evidence class: DESK_RESEARCH ONLY.** URLs checked against upstream public documentation/repositories on 2026-11-01. No external candidate was installed, run or benchmarked in ProtocolIA here. Scores are intentionally **not** awarded for claimed capabilities; tests precede selection.

## Discovery, specification and orchestration

| Candidate | Current verified upstream signal | Hypothesis to test | Integration risk / conditional decision |
|---|---|---|---|
| [Superpowers](https://github.com/obra/superpowers) | MIT. Current releases discuss codebase-first brainstorming, fresh builder checks, and execution with final review; workflows differ by version. | Strong adversarial clarification and requirements review. | Never embed generic human approval gates in autonomous default; test current pinned skill version, prompts, tool support and opt-out telemetry. |
| [GitHub Spec Kit](https://github.com/github/spec-kit) | MIT; customizable workflows/presets/extensions for SDD, bug fixes and evidence-backed idea assessment. | Cohesive chain from requirements to implementation and coherence checks. | Must map spec artifacts to TypeSpec; no duplication of executable semantics, no mandatory service. |
| [OpenSpec / OPSX](https://github.com/Fission-AI/OpenSpec) | MIT; OPSX action-based workflow with `propose/explore/apply/update/sync/archive`, schemas and editable Markdown change artifacts. Legacy commands migrated. | Explicit change proposals, archival, rehydration across sessions. | Markdown change records are not executable IR; test delta-to-TypeSpec mapping and conflict detection. Pin OPSX release. |
| [GSD Core](https://github.com/open-gsd/gsd-core) | MIT; active successor to **archived** `gsd-build/get-shit-done`, supports phase loop discuss/plan/execute/verify/ship and multiple agent harnesses. | Unattended phased development with compact state, isolated agents and checkpoints. | Must test safety gates, headless operation, resource cost, action permissions and conflicts with ProtocolIA's own verifier. Use successor, not archived upstream. |
| [BMAD Method](https://bmadcode.com/method) | MIT; role/workflow-oriented analysis, specification and implementation process. | Independent critic for complex domain discovery. | Higher agent coordination/context cost; not justified for simple CRUD without measured benefit. |

**Initial experiment arms, not a winning stack:** `Superpowers + OpenSpec` vs `Spec Kit + TypeSpec` vs `GSD Core + OpenSpec + TypeSpec`; test a BMAD-based critic as an optional sub-experiment. Each arm gets the **same frozen user requirements** and same harness budget; ProtocolIA core is the common execution verifier for contracts that compile.

## Generation, documentation, architecture and verification

| Layer | Candidate(s) | Why test it / measurement | Key caveat |
|---|---|---|---|
| Semantic core | [TypeSpec](https://typespec.io/) + existing IR | Preserve current verified Spring/Nest generation, real DB and API parity; measure unsupported contracts | Do not replace with prose-only specifications. |
| Admin UI | [Refine](https://github.com/refinedev/refine), [React-admin](https://github.com/marmelab/react-admin) | Build same bounded 4-entity app; compare React maintainability, accessibility, custom forms, mobile workflows, adapter size and regeneration | Both have MIT open-source cores; evaluate any separately licensed/pro add-ons before use. |
| Architecture-as-code | [LikeC4](https://likec4.dev/), [Mermaid](https://mermaid.js.org/) | TypeSpec/IR -> typed diagram assertions; compare linkability, diagram diff, export portability and validation | LikeC4 may add an independent DSL; don't let it become second domain source. |
| Documentation | [Starlight](https://github.com/withastro/starlight), [Zensical](https://github.com/zensical/zensical) | Searchable generated docs, static/offline handoff, GitHub Pages and diffs | Evaluate dependency/cost and Markdown file longevity. |
| API adversarial tests | [Schemathesis](https://github.com/schemathesis/schemathesis) | Stateful OpenAPI fuzzing of a **disposable** generated app | Requires meaningful links/seed/auth; does not prove financial correctness or domain invariants. It performs real writes; never point at production. |
| Browser conformance | Existing Playwright/Chromium | Continue real mobile/desktop integration tests | Do not mistake screenshot success for permissions or transactional correctness. |
| Technical decisions | ADR/MADR text files | Human-intended rationale and alternatives versioned in Git | Source generation alone cannot infer business motivation. |

## Licensing / maintenance diligence

The upstream repositories for Superpowers, Spec Kit, OpenSpec, GSD Core, Refine core, React-admin core, LikeC4, Starlight, Zensical and Schemathesis describe MIT licensing in the referenced pages or licenses as of this review. **This does not cover every commercial addon, transitive dependency or future version.** Before adopting, pin an exact tag/commit, read the full license and transitive notice obligations, check recent releases/security advisories and run reproducible installation tests.

## Explicit kill criteria

1. Reject any candidate that silently turns a material business assumption into an approved contract.
2. Reject any candidate that requires automatic privileged external actions or unbounded permissions for basic analysis.
3. Reject integrations that create another editable semantic authority conflicting with TypeSpec/IR.
4. Reject unmaintained/archived tooling when an actively maintained replacement exists (unless pinned for historical comparison).
5. Reject an adapter if the same independent application acceptance needs post-generation domain code edits that the baseline avoids.
6. Reject a candidate if measured total owner+agent effort, reproducibility or correctness is worse with no counterbalancing benefit.
