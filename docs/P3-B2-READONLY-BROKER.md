# P3-B2.1 — Typed plan to trusted-host read-only broker

P3-B2.1 integrates ONE existing isolated `file.sha256` Docker action into a separately versioned, typed v0.5 execution DAG, with pure deterministic steps and equality postconditions. The v0.4 SQLite action executor remains unchanged. These two executors are **not** one atomic transaction.

The agent supplies only a strict `version=0.5` DAG of `literal`, `sha256`, `assert.eq`, and `file.sha256`; a maximum of **one** Docker read is allowed. Its capability and effects declarations must exactly match the closed registry. It cannot select host file paths, policies, Docker flags, images, executable code or signing keys.

A trusted host separately supplies a versioned policy with exact grants, action/read budgets and total time. A second host policy fixes Docker's local immutable image ID, resource allowlist, byte limit, max duration and known paid-provider cost 0. `preview_plan` computes a bounded file digest and an immutable derived external request ID from the *entire normalized plan* and the trusted broker policy. It creates no approval. `approve_plan` must run only in a trusted, operator-authenticated host service holding a secret, NOT in any model-selected tool interface. `run_plan` can act only after that HMAC-signed approval has been issued by the host, with exact bound input, policy, declared operator identity, environment and tool fingerprint.

The read-only Docker adapter persists one attempt before Docker starts; the repeated plan reuses the completed result, and an ambiguous crash/failure is quarantined instead of retried. A failed subsequent assertion **does not undo** the already performed read, but cannot create external writes or duplicate an external operation. The result includes a plan hash, policy hash, and SHA of separately checked external evidence. Docker's real `--network none`, `--read-only`, `--cap-drop ALL` confinement was verified in P3-B1, and the P3-B2 integration runs a live container and a separate ProtocolIA-Test consumer.

**No production-ready authorization claim:** the `subject` string remains asserted by the caller. There is no OIDC/SSO, authenticated browser approval interface, hardware key, paid vendor accounting, dynamic tool permission broker, writable external effect or compensation mechanism. Docker daemon and host inputs remain privileged trusted dependencies. The design explicitly rejects multiple external effects or any spend beyond known-zero and is not a general-purpose agent runtime.

Next P3-B2 steps: trustworthy operator authentication and signing-key custody/rotation, exact permitted effect approval UI/broker, accounting and durable recovery for potentially paid/writable operations, and hostile-container independent escape testing. Issue #4 stays open.
