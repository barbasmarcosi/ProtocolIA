# A6 — Contract-driven guarded business state transitions

**Increment:** TypeSpec metadata `@initial` on a required string field and `@transition(from,to)` on a `@behavior("transition",entity,field)` POST operation. This is a **bounded state-machine primitive**, not a general workflow/orchestration engine.

## Implementation

- Source: `examples/vnext/work-orders/contracts/main.tsp` (independent domain, unmodified Taller/Gauge/Equipment contracts).
- Canonical IR `vnext-a0.1` retains `initial` and transition `field/from/to`. `@protocolia/domain` and the compiler enforce valid states, nonpublic mutation, field compatibility, no state-field PATCH bypass, source != target, and success 200 / conflict 409. Adapters reject unsupported/malformed transition semantics before emitting code.
- Both modular Spring Boot/JDBC and NestJS/pg emit `UPDATE ... SET status=to WHERE public_identity=key AND status=from`: one atomic SQL update, no get-then-update race; absent row -> 404, invalid precondition -> 409, unauthorized -> 401/403. Creation accepts only the declared initial state; PostgreSQL CHECK constrains values to contract-defined states.
- Shared React/Vite generates read-only initial status in the create form and context-sensitive state-action buttons from `transitions[]` in each generated UI manifest. No code branches by domain/entity names.
- Generic conformance derives initial values and transition routes/states from each generated manifest; a separate exact-workflow HTTP test covers business acceptance, including ten competing approvals.
- Safety: no arbitrary SQL, source snippets or JS code accepted through the TypeSpec decorator; transition state tokens are constrained to a safe finite identifier grammar.

## Remaining acceptance boundary

- **A6 dynamic React buttons in Chromium NOT RUN**: source/manifest generation and Vite build observed, but the new workflow buttons have not yet been clicked in a browser E2E test.
- A6 currently supports constant-string field transitions and a fixed initial state. No conditional guards across multiple entities, custom business effects, approvals with audit trails, timers, compensation, outbox, payments or OIDC.
- Model permits direct **authorized** DB access by a privileged DB operator. The SQL CHECK only restricts known state values, not privileged direct transitions; transactional guards are enforced at generated API boundary.
- PostgreSQL containers in the Render build are disposable. Render public URL is marker-only. Docker Engine `compose up`, operational backup/restore and production IAM are still not validated.

**Value:** ProtocolIA now executes a stateful business operation from contract semantics in both supported backends; this is an actual behavior, beyond scaffolding/CRUD.
