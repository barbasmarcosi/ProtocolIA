# A12 — A10→A11 audited application in-place evolution

## Why

A11 proved fresh generation of a separately authorized, paginated audit history reader in Spring Boot 4/NestJS 11 + React, but **not** upgrade of an already-running A10 app with real PostgreSQL rows and a populated `protocolia_audit_event` journal.

A12 extends the existing `protocolia plan/evolve` contract-differ and staged atomic regeneration for this **read-only, zero-DDL** profile. No changes to already-audited writes, storage, or the canonical IR version.

## Scope and acceptance rules

- Source: `examples/vnext/work-orders-a10`; exact A10 WorkOrder domain, audited create and guarded approve/close, and no auditPage. Evolved source: `examples/vnext/work-orders` with `auditPage` GET `/api/work-orders/{code}/audit` and dedicated `orders.audit` capability.
- Only append a single independently authorized `auditPage` on a previously audited entity. The original auditable create/transition operations must match byte-for-byte as JSON; no existing operation, route, capability or field may change. New auditPage may not mutate, be anonymous, reuse ordinary read/write privileges, or accept a nonpublic identity path.
- OpenAPI validation permits **new response schemas reachable from only the newly added audit endpoint**, while preserving the preexisting OpenAPI paths and component schemas verbatim. Unreachable new schemas or modifications to existing request/response models fail closed. This avoids accepting hidden API drift.
- `additiveSql(plan)` produces the empty string: no V2 migration file for adding read-only API/UI, no migration-history changes, no journal replay, no SQL backfill.
- `evolve` uses the existing integrity seal, preflight checks, staged project rebuild, consumer `extensions/` preservation, original Flyway V1 and Nest baseline/SQL patch restoration, Spring jar repackage and atomic directory swap with backup. It does **not** run database transactions itself; DB preservation is observed over restart.

## Empirical scenario — both targets

The same isolated Render Free Docker build executes `scripts/vnext/probe-a12-audit-upgrade.sh` after all A0–A11 regressions:

1. Build an **independent A10 app** from its own TypeSpec source into Spring/Nest targets, copy to deployment path, launch each on a freshly initialized dedicated PostgreSQL 16 database.
2. Execute existing ten-way approval race and state transitions; create an independent second WorkOrder. Assert six original audit events (four on W-001, two on W-AUDFAIL), two domain rows, and **no old audit-query route or audit-reader capability**. Snapshot exact audit IDs/actors/before/after and underlying SQL V1/baseline.
3. Check the CLI plans one compatible read-only `addOperation` with kind `auditPage`; reject a validly compiled but unsafe attempted change to a **historical audited writer**, without touching the sealed deployment.
4. Evolve original deployment in place via ProtocolIA CLI. Verify original V1/SQ​L baseline byte-for-byte, **no new migration file**, exact journal and row data, consumer extensions, and ownership integrity.
5. Restart the evolved app **against the original DB**, exercise A11 independent reader authorization (401/403/404/400), strict pagination and resource isolation, and inspect React generated manager history/reader hidden via Chromium 390×844. Reverify original journal rows unchanged and Flyway/Nest migration history unchanged.
6. Repeat `plan`/`evolve` and application startup, assert **no changes** and that domain rows and audit data remain.

A dedicated Node unit test validates compatible read-only operation addition and rejects tampering, shadow routes, capability reuse, public access, hidden OpenAPI schema/validator drift, additional mutations or request/output changes.

## Known boundaries

The A12 profile is narrowly limited to a **read-only auditPage operation** on an A10 source that already contains the audited event table. There is no transition to full production IAM/OIDC, cryptographically immutable journal, retention/backup policy or automated database rollback; no online dual-version zero-downtime migration or concurrent writer cutover test. The public Render service is only a verification marker, not the app itself.
