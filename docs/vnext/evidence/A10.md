# A10 — Auditable contract-defined business mutations (bounded)

## Goal

Add genuinely generated **transactional audit records**, not domain-specific hand-written event code. The audited example is the independent `examples/vnext/work-orders/contracts/main.tsp` contract. TypeSpec declares explicit audit fields on ordinary business operations:

```typespec
@post @behavior("create","WorkOrder") @audit("title,status") @capability("orders.write")
op createWorkOrder(...): ...;

@post @behavior("transition","WorkOrder","status")
@transition("draft","approved") @audit("status") @capability("orders.write")
op approveWorkOrder(...): ...;
```

- `@audit("field1,field2")` opts in to **named fields**, with 1–8 unique fields belonging to the same entity. Source contracts may not audit arbitrary request bodies. Current bounded profile supports **create and state transitions** only; transition audit permits only its guarded state field. Unknown fields, duplicated fields, use on reads and excessive fields are compiler errors. Both adapter generators independently reject malformed IR.
- Canonical IR retains `behavior.audit: string[]` and both generators create `protocolia_audit_event` with append-only **API behavior** (BIGSERIAL key, PostgreSQL server timestamp, authenticated actor, entity, public identity, operation, selected field, before and after as text). The generated API provides no update or delete audit endpoint. This is **not tamper-proof** to privileged SQL operators; no signed/hash-chained records, external archival or compliance certification.
- **Spring**: the dispatch handler already runs inside `@Transactional`, writes one audit row per allowlisted field **after the successful domain effect but before transaction commit**. Failure inserting audit rows rolls back business mutation.
- **NestJS**: creates and guarded transitions use a pinned `pg` connection with `BEGIN/COMMIT/ROLLBACK` for domain and audit writes together. Release/restock transitions incorporate audit into their already existing transaction, and audited simple transitions become transactional. Actor comes from authenticated server-side session; no trust in caller-supplied usernames.
- Failed/unauthorized/duplicate operations must not produce records. Concurrent guarded transitions emit only events for successful transitions. Created rows audit `before=null`, while transitions record declared source/destination states.

## Actual verification

Implementation source and test gate are checked into the PR branch; Render Free service `srv-db6t203rjlhs7395vjn0`, deploy `dep-db7fkidg1s2s73abvlj0`, started from source `ed7e12e7a7ca1eb17df33062d8181c96afb014ea`.

The new independent `ServiceCase` IR fixture validates both generators and rejects unsafe selected fields. A WorkOrder TypeSpec fixture validates compiler semantics; negative TypeSpec variants reject unknown or repeated fields and @audit on read operations.

The existing `scripts/vnext/probe-workflow-postgres.sh` runs both generated runtimes against two real disposable PostgreSQL databases, first exercising the full A6 HTTP/conformance state machine, then directly verifying event rows, authenticated user, before/after values, and no events for failed requests. It also injects a PostgreSQL trigger that deliberately breaks audit inserts. Both **create and transition must return 5xx and leave business state rolled back**, followed by removal of the injected fault.

**Empirical results — PASS bounded, both Spring and Nest.** The corrected source `9cf1032817b98088616f1838b9d7419c6c204e24` was executed in Render Free deploy `dep-db7fp2u7bikc73anp7ug`. Node **41/41 PASS** including an independent `ServiceCase` IR audit fixture. TypeSpec rejected every mutated `@audit` fixture with `A10_INVALID_TYPE_SPEC_AUDIT_ALLOWLIST_REJECTED_PASS`. The WorkOrder TypeSpec compiled to both targets, with matching canonical IR/OpenAPI SHA-256.

The two PostgreSQL-backed HTTP suites produced:

Direct `psql` validated four exact entries for `W-001` (created title + state, approved state, closed state), actor `manager`, old/new values and non-null timestamps. Rejected create/write and wrong-state attempts did not append entries. A deliberate `BEFORE INSERT` PostgreSQL trigger refused writes to the audit table; both generated backends returned errors and rolled back **both CREATE and state transitions**, with the domain row absent or still `draft` respectively. After removing the trigger, normal writes and audit inserts resumed. The tests also verified A6 state-machine behavior remained functional.

The word *IMMUTABLE* in the probe marker refers to a fixed observed journal sequence, **not** a database-level tamper-prevention guarantee. A privileged PostgreSQL role can modify/delete audit rows; they are append-only only through the generated API. The same Render Free build `dep-db7fp2u7bikc73anp7ug` completed all A0–A9 regression gates successfully, including NestJS/Spring HTTP/PostgreSQL, earlier Chromium and A5/A9 Flyway+Nest V1→V2 evolution. Render verified the deploy as **LIVE**, source commit `9cf1032817b98088616f1838b9d7419c6c204e24`. The public endpoint is only a build marker, not the generated audited application. Maven used `-DskipTests`; domain behavior was verified independently with real PostgreSQL and HTTP.

## Explicit limitations

- Only explicitly annotated create/state-transition operations are audited; patch, increment and delete currently remain **unsupported**, not silently logged.
- Text snapshots are expressly selected by contract author. Do not select secrets, credentials, or high-sensitivity fields. **No automatic PII masking** exists.
- Historical A9 apps do not automatically acquire audit tables when upgrading: this A10 audit profile is tested on freshly generated WorkOrder databases; audited evolution of existing deployments requires separate migration/journal support.
- Audit data can currently be inspected in PostgreSQL. **No generated authenticated audit-query HTTP endpoint or React audit-history screen yet.**
- Current authentication in evidence is opt-in demo Basic; not production IAM/OIDC. No retention policy, immutable offsite log, tamper-evident signing, backup/restore or external SIEM integration.
