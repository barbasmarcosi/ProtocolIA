# A14.3/C16 — Durable overdue alerts and delivery

Date: 2026-10-14. Branch `feature/vnext-a0-typespec-jhipster-spike`; PR #52.
Historical A13 contract and result `13/16` stay frozen. This is a **separate A14.3 contract**: `examples/vnext/facility-maintenance-a143`.

## Product boundary

An alert detected and saved in PostgreSQL **is not equivalent to a delivered notification**. The first slice is an in-app **pending outbox**, not an email/push delivery service. A normal REST request cannot provide a guarantee of asynchronous wake-ups when a process is asleep. No notification SLA or exactly-once external effect is claimed.

## Implemented slice A14.3-S1 — Contract + durable inbox projection

- TypeSpec `@overdueAlert("dueAt","status","completed","technicianBadge","inbox")` on a declarative entity contract; compiler emits semantic IR, never executable code from the contract.
- Compiler rejects missing/incorrect due timestamp, non-finite-state status, undeclared or nonterminal final state, non-required recipient FK, unsafe values and any channel except `inbox`.
- Both Spring and Nest generators use the **same shared** `packages/adapters/overdue-policy.mjs` to create `protocolia_notification_outbox`, a pending/available-at index, and a `protocolia_materialize_<entity>_overdue(as_of TIMESTAMPTZ)` function. A unique `(rule_key,resource_id)` constraint plus `ON CONFLICT DO NOTHING` avoid duplicate alerts in repeated scans. Clock is injected as a SQL parameter.
- The generated rule manifest `protocolia-overdue-rules.json` is identical on both targets. No entity-specific logic was written in either backend adapter.
- The old unannotated contract does not produce notification tables/functions. Changes to an existing persisted application's `overdueAlert` are **rejected** by `diffContracts` until a dedicated, proven additive migration exists.
- First green real Actions [run #38650987559](https://github.com/barbasmarcosi/ProtocolIA/actions/runs/38650987559), code commit `ba98fcb9bc07772f6c3d2adb7af8a0ea0e1b36a6`: independent 3/3 Node tests, official TypeSpec compilation of A143, Spring/Nest generator rule equivalence, real PostgreSQL forced-clock fixture for overdue vs future/completed tickets, deduplication, recipient FK selection, and durability through actual PostgreSQL restart **PASS ×2**. Later hardening commits require their own CI confirmation.

### Scope caution

A single insert with an immutable unique key demonstrates **deduplicated alert creation**, not durable dispatch and not losslessness during simultaneous business mutations and scans. The generated table is an inbox/outbox precursor, not a transactional outbox sourced from mutation commits; a periodic materializer must compensate through rescans. The C16 requirement remains OPEN.

## S2a — Transactional internal inbox receipt (implemented; empirical rerun pending)

The canonical policy generator also emits a **recipient-indexed** `protocolia_notification_inbox` table and bounded `protocolia_dispatch_inbox(batch_size)` stored function. It selects up to 100 pending events with `FOR UPDATE SKIP LOCKED`, materializes the recipient's inbox entry with `ON CONFLICT DO NOTHING`, and transitions the corresponding outbox row to `delivered` with an internal delivery timestamp and attempt counter **in the same PostgreSQL statement transaction**. This is an *internal database receipt only*; it must never be presented as evidence of an email/push delivery. The SQL is generated for both Spring and Nest from one shared source.

The expanded `probe-a143-inbox-postgres.sh` tests fault-injected failure of inbox writes with full rollback, concurrent database clients racing the same notification, duplicate dispatch returning zero, bounded request rejection and durable receipts through an additional PostgreSQL restart. The source was committed on the branch, but **not yet declared PASS** pending the specific green Actions job for the updated commit.

**Still needed for actual C16:** automatically scheduled recurring scans, worker crash/retry/dead-letter management, independently authorized recipient-scoped HTTP/UI access, safe additive evolution from a populated older schema, external channel delivery/receipts if required, and sustained deployment validation.
