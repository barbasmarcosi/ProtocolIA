# A7 — Contract-derived atomic reservation spanning two entities

## Scope and contract

Source of truth: `examples/vnext/inventory-reservations/contracts/main.tsp`. It declares two independent entities, `Part` (`sku`, `name`, `available`) and `Allocation` (`number`, `partSku`, `units`, with FK `Allocation.partSku → Part.sku`).

The mutation is still a normal contract POST/create endpoint. A single semantic decorator supplies the invariant:

```typespec
@post
@behavior("create", "Allocation")
@reserve("Part", "available", "partSku", "units")
@capability("allocations.write")
op createAllocation(@body input: AllocationRequest):
  { @statusCode _: 201; @body allocation: Allocation; }
  | Conflict | BadRequest | Unauthorized | Forbidden;
```

The compiler validates that the stock field is a required `int32` with minimum zero; that the reservation amount is a required positive `int32`; that the reservation holds a required FK to the declared stock entity's public key; and that the request model contains a required identity, FK and positive amount. Invalid decorators fail closed. JHipster/JDL remains an explicitly incomplete projection.

Both adapters consume the *same* TypeSpec and IR `vnext-a0.1`:
- **Spring Boot JDBC:** inside the already-transactional HTTP handler, `UPDATE part SET available=available-:amount WHERE sku=:stock AND available>=:amount`, then `INSERT allocation`. Any constraint/duplicate failure rolls the entire operation back.
- **NestJS `pg`:** one acquired PostgreSQL connection runs `BEGIN`, the same conditional stock debit, reservation insert and `COMMIT`. On any exception the transaction is rolled back and the connection released.
- Additional authority check requires both the reservation create capability **and the parent stock create/write capability**, denying a cross-entity write escalation.
- Insufficient stock yields HTTP 409; absent parent yields 400; duplicate reservation identity returns 409 and leaves stock unchanged; invalid input and unauthorized access yield 400/401/403. PostgreSQL nonnegative CHECK and FK RESTRICT are retained.
- Shared React/Vite reuses its generic per-entity forms and FK selector; no domain-specific backend or frontend code was added. The targeted A7 user-interface journey in Chromium has **NOT RUN**.

## Honest acceptance boundary

**PASS bounded:** one reservation creation, one conditional debit in another table, positive int32 units, referential integrity, duplicate rollback, and concurrent no-oversell. These are live PostgreSQL transactions from generated code, not a scaffold demonstration.

**Not demonstrated/implemented:** general multi-step workflow orchestration; multi-stock reservations in one request; release/refund/cancellation and reversal; expiration; audit/outbox/events; arbitrary declarative computations; isolation-level tuning, production IAM and backups. No direct delete operation was generated for Allocation to imply stock restitution; reservations currently represent committed consumption until a future explicit compensation primitive is defined. DB superusers can still manipulate data outside the generated API.

Render's public HTTP endpoint remains a **build marker**, not the generated inventory application. Docker Engine real `compose up` remains **NOT RUN**. Historic P3/P4/G0–G5, `main`, and unrelated resources are preserved.
