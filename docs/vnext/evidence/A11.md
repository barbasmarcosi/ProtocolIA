# A11 — Contract-driven audit history (read endpoint and React)

## Objective

Expose the **already generated A10 audit journal** from an explicit TypeSpec contract, with separate authorization, bounded server-side pagination and a generated React resource-detail history. This is a reusable generator capability, not a WorkOrder-specific endpoint or hardcoded UI.

```typespec
@route("/api/work-orders/{code}/audit")
@get @behavior("auditPage", "WorkOrder") @capability("orders.audit")
op listWorkOrderAudit(
  @path code: string,
  @query @minValue(1) @maxValue(50) limit?: int32 = 25,
  @query @minValue(0) @maxValue(1000000) offset?: int32 = 0
): AuditPage | NotFound | BadRequest | Unauthorized | Forbidden;
```

- The new `auditPage` **reads** canonical `protocolia_audit_event` rows persisted by A10. Compiler enforces a GET identity path, no input body or mutation decorators, explicit pagination query inputs, 200/400/404, and a **distinct nonpublic audit capability** not equal to the entity's normal read or write capability. No duplicate auditPage per entity and no auditPage without auditable entity operations. Both Spring/Nest generators independently reject unsafe IR.
- Manager demo authority explicitly includes `orders.audit`, reader demo role does not. Both backends apply capability checks **before** looking up the entity, so readers cannot enumerate resource existence through the audit endpoint. The dedicated role is distinct; neither standard `orders.read` nor `orders.write` grants audit access by itself.
- Generated GET implementation validates integer `limit` (1..50, default 25), `offset` (0..1,000,000, default 0), rejects unknown query parameters, checks target entity existence (404), binds SQL query parameters, filters by entity + resource identity, orders by monotonically increasing audit id **descending**, and returns `{items,total,limit,offset}`. Events expose `id` as a string, actor, entity, resource ID, operation, field, before/after, UTC ISO timestamp. No arbitrary SQL or record-wide exports.
- React resource detail reads the audit operation from generated `protocolia-ui.json`. An authenticated user with the **audit-specific capability** sees a compact, paginated audit table; unauthorized users do not see the history at all. Values are rendered as React text; no raw HTML. It uses the existing session and handles API errors.

**Source under validation:** `910ad345e2de2b7343cf3d1eaed6366dc3d9a967`; existing Render Free deploy `dep-db7g4iij9qps73cb5fm0` on service `srv-db6t203rjlhs7395vjn0`.

- Independent `ServiceCase` IR unit tests confirm Spring/Nest generated manifests, audience, SQL readers and UI manifest; invalid capability sharing and missing event source are denied.
- TypeSpec negative cases independently reject using `orders.read`, `orders.write`, `public` or POST for the audit query.
- For each target, after a real A10 creation and guarded transition sequence and deliberate fault-injection rollback, `scripts/vnext/probe-a11-audit-http.mjs` asserts unauthenticated 401, reader 403 including missing IDs, manager 404 for missing IDs, 400 for illegal pagination, exact reverse-chronological records with field/actor/time, two paginated requests reproducing all four entries, and isolation between two order identities.
- `scripts/vnext/probe-a11-audit-browser.mjs` exercises a real generated React UI with Chromium viewport 390×844. Manager sees the four changes; reader can still view the order but sees **no audit history**.
- Existing A0–A10 regression suite runs unchanged in the same Render build, including Spring/Nest PostgreSQL transactions, A9 persisted migration, Flyway and Nest migration journals, and Chromium.
- **Status:** do not declare PASS until the actual logs confirm the HTTP/DB/Chromium probes and full build. Render public endpoint is a build-status marker; it is **not** the generated WorkOrder application.

## Scope constraints

- This read capability is available on freshly generated A11 apps with A10 event journaling. It does **not** provide online audit endpoint evolution/migrations for an already deployed A10 database yet.
- Pagination is offset-based and deterministic by event id for an unchanged dataset; concurrent newly appended events can move offset pages. Cursor pagination is not yet supported.
- The audit journal remains writable by privileged PostgreSQL administrators. No cryptographic append-only guarantees, WORM storage, redaction, retention schedule, backup/restore, OIDC or production authorization. Contract authors must not audit sensitive fields.
