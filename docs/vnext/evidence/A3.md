## Qué se implementó

- **Target independiente** `packages/adapters/nest/generate.mjs`: lee IR/OpenAPI oficiales, falla temprano ante entidades/rutas/métodos/status/capabilities/tipos/identidades ambiguos, emite proyecto NestJS compilable, manifiesto, SQL Postgres con FK restrict, React/Vite y Compose localhost-only. Nunca requiere `java` ni Maven.
- **Runtime compartido** `packages/adapters/nest/templates/main.ts`: `@Controller` de Nest por operación semántica, rutas de identidad pública, PostgreSQL mediante `pg` y parámetros SQL, transacciones por sentencia atómica, verificación de esquema al arrancar mediante huella en `protocolia_schema_history`, auth Basic exclusivamente demo opt-in y endpoint `/api/_protocolia/me`, validaciones de JSON, paginación, `create/get/listPage/patchFields/atomicIncrement/delete`, 404/400/401/403/409.
- **La misma plantilla de React** utilizada por Spring se distribuye con Nest; formularios/detalle/listado/roles no codificados por entidad.
- **CLI extendida**: `npm run app:build -- examples/vnext/taller --target nestjs --out dist/nest-taller`. `app:run/test` reconoce empaquetado Nest por target; `app:evolve` falla cerrado para Nest hasta implementar migraciones aditivas propias (no intenta aplicar Flyway Spring sobre Nest).
- La suite genérica `packages/cli/conformance.mjs` resuelve el manifiesto según el target, sin requerir tests escritos por entidad ni cambiar el contrato.

## Fallos resueltos con evidencia

1. Primer arranque Nest falló al no incluir el usuario PostgreSQL explícitamente en la URI `pg`. El runtime ahora construye una URL de conexión válida a partir de las mismas variables que utiliza Spring; recompiló y arrancó.
2. La conformance compartida asumía la ubicación de `protocolia-ui.json` propia de Spring. Se hizo target-aware; Taller Nest HTTP, Chromium y conformance pasaron.
3. Un script Bash imprimía un marcador utilizando `$name_HTTP...`, creando una variable inexistente en `set -u`. Se corrigió a `\${name}` en el script (sin cambios de código negocio). Ambas suites terminaron PASS.

## P-01…P-06 y límites

- **P-01:** PASS — contrato/IR/OpenAPI idénticos en Spring y Nest para Taller y Gauge.
- **P-02:** PASS — T-02…T-15 en HTTP/PostgreSQL real, estados y efectos equivalentes, incluidos incrementos concurrentes y auth.
- **P-03:** PASS acotado — JSON y queries inválidas, roles protegidos y rutas conocidas. Sin fuzzing avanzado de HTTP.
- **P-04:** PASS — schemas PostgreSQL generados independientemente con invariantes y filas persistidas durante la conformance; esquema-huella de Nest rechaza drift en próximos arranques por diseño, pero esa negativa aún no fue testeada por separado.
- **P-05:** PASS — pruebas negativas del adaptador rechazaron mutations de capability, identidad, status, tipos y OpenAPI sin generar outputs falsos.
- **P-06:** **PENDIENTE** — `app:evolve` soporta únicamente Spring+Flyway, no regeneración aditiva en Nest con DB existente. El generador Nest rechaza overwrite de outputs no vacíos; ownership preserva la distinción de archivos, pero esto no cierra P-06.
- El Docker Compose emitido con target Nest **no fue ejecutado por Docker Engine**; su ciclo end-to-end sigue pendiente de A2, al igual que Spring. No ejecutar tests contra sistemas con datos de usuario.
- La autenticación Basic es **demo de prueba opt-in**, no JWT/OIDC listo para Internet. Nest requiere hardening antes de producción.
- Nest no invoca OpenAPI Generator para crear interfaces tipadas: consume OpenAPI oficial para límites y valida su semántica junto al IR, pero el controlador se crea desde operaciones del manifiesto. No presentar DTO Java ni Nest como delegates OpenAPI generados.
- Sin upgrade seguro Nest de tablas existentes, sin backup DB automático, sin TLS/IAM productivo. Ningún GitHub Actions ni proveedor pago fue utilizado.

**Estado real A3: paridad funcional probada, alcance acotado; P-06 explícitamente abierto.** No se modificó `main` ni se publicó la app NestJS como demo pública.
