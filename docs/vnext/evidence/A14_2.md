# A14.2 — Declarative query page (first implementation slice)

Date: 2026-10-14. Work branch: `feature/vnext-a0-typespec-jhipster-spike`, PR #52.
The independent A13 contract and its historical 13/16 verdict remain **unchanged**. This feature uses `examples/vnext/facility-maintenance-a142/contracts/main.tsp`, derived from but separate from A14.1.

## What was implemented

- `@queryFilter("path","eq|gte|lte")` on optional official TypeSpec HTTP `@query` parameters, and `@queryOrder("field","asc|desc")` on a `@behavior("queryPage",entity)` operation.
- Canonical IR has explicit query predicate type, parameter, local field or **one-hop** outgoing FK, and deterministic declared order. The official OpenAPI schema is independently checked for parameter names, optionality, type and datetime format before either generator runs.
- A shared `packages/adapters/query-plan.mjs` compiles only known identifiers and operators. Filter *values never enter SQL text*. Both Spring and Nest get equivalent whitelisted plans with bound values, bounded limit/offset, count query, UTC datetime parsing, deterministic identity tie-break and NULLS LAST.
- PostgreSQL `CREATE INDEX IF NOT EXISTS` is generated for direct and one-hop filtered columns (existing primary keys are reused). Duplicate DDL is de-duplicated. A5 can add the new read-only operation, preserving the old baseline, and produce additive SQL index migrations.
- React's generated UI exposes typed filter controls on the entity page, applies/clears filters and preserves paginated query state. The existing unfiltered `listPage` stays available and reference pickers remain unchanged.
- Independent example searches tickets by `Machine.siteCode`, status, and optional inclusive due-date lower/upper bounds. It does not include a Ticket-specific query implementation in any adapter.

## Reuse decision

Retain official TypeSpec HTTP/OpenAPI decorators and the existing `NamedParameterJdbcTemplate` (Spring) and `pg` parameter binding (Nest). [Kysely](https://www.kysely.dev/docs/intro) is a mature query-builder option but brings a new dependency and typed-schema integration needs for each generated application; current explicitly allowlisted one-hop predicates do not yet justify it. Do not implement arbitrary runtime SQL expression parsing, a private schema DSL or a new database driver.

## Known limits and follow-ups

- Sorting is contract-declared (field and direction), not yet end-user selectable from multiple permitted sort fields.
- Only `eq`, inclusive `gte` / `lte` on scalar fields, one-hop outgoing required FK, and a maximum of eight filters are supported. No full-text search, OR expressions, nullable `IS NULL`, tenant-global ACL or multi-hop joins.
- The demo Basic-auth profile is not production IAM. A generated query must not be advertised as tenant-safe until row-level/tenant authorization is explicitly modeled.
- Generated additive indexes use standard transactional `CREATE INDEX IF NOT EXISTS`. On large populated production tables these can block writes; future zero-downtime index rollout needs a separately audited migration strategy (for example PostgreSQL CONCURRENTLY outside Flyway's default transaction).
- Next action with compute available: run isolated tests first; fix failures in their architectural layer, then run real PostgreSQL and mobile probes and only after that update C15 classification.
