# A9 — Safe in-place A7→A8 migration and Chromium acceptance

## Change implemented

The legacy A7 TypeSpec contract is preserved verbatim in `examples/vnext/inventory-reservations-v1/contracts/main.tsp` from functional source `ad34b7f2d33c123cfd404d30e12fe18d58ab4a97`. The current A8 contract adds a required `Allocation.status` with `@initial("active")` and the guarded `@release` transition. The **create request now accepts optional status**, and both server adapters supply `active` if omitted; explicitly supplied `cancelled` remains HTTP 400. This preserves A7 clients at the API boundary.

The `app:plan/evolve` compatibility checker accepts only a narrowly defined, contract-proven state migration:
- One new required non-null state string field with a safe fixed `@initial` value.
- Exactly one new guarded, terminal `@transition` + `@release` operation on this field, with a matching existing `@reserve` creation operation and unchanged write capability.
- Every previously declared operation and field remains structurally identical. Existing OpenAPI routes, models and validators are compared canonically, subtracting **only** the verified new state property and cancellation route. The create DTO must keep the new state optional.
- A generated SQL V2 adds the state with `DEFAULT 'active' NOT NULL` and a finite-state CHECK, backfilling historical rows without modifying V1 migration bytes. Normal additive optional fields retain their previous A5 behavior. Unsupported modifications fail closed before regeneration.

The migration runs through the existing staging/ownership-seal workflow and leaves consumer extensions intact. Spring uses Flyway V2 and Nest uses its checksummed transactionally applied V2 journal; neither silently recreates the DB. The migration is forward-only; there is **no automatic rollback/downgrade**.

## Acceptance suite

`scripts/vnext/probe-a9-in-place.sh` uses **two actual PostgreSQL 16 databases** and two generated framework targets. For each, the suite:

1. Builds/runs the historical A7 application and seeds `Part P-MIG` with 12 units and two `Allocation` rows (3+2 units); verifies available = 7 and that the original responses have no `status`.
2. Stops the app, runs `app:plan` and `app:evolve` using the current TypeSpec. Verifies plan reports compatible with precisely `addInitialState` and `addOperation`, original V1 schema is byte-for-byte preserved, V2 contains safe SQL/default/check, owned extensions survive and ownership seal passes.
3. Restarts the **upgraded generated server against the same DB**, confirms both old rows now have `active` without changing their identities, quantities or stock. Cancels one old row, verifies one-time credit, and sends an unchanged A7 client request with no `status`, expecting a successful new `active` reservation.
4. Runs a **real Chromium React** flow at mobile-width 390×844: manager signs in, opens historic `R-LEGACY`, clicks the generated contract-derived cancel button, sees state `cancelled`, switches to Part listing, sees restored quantity. Reader subsequently signs in and cannot see the cancel button.
5. Checks PostgreSQL counts, available balance, Flyway/Nest journal version V2, and data preservation after a second server restart.

Unit tests in `tests/vnext/state-migration.test.mjs` check exact SQL, OpenAPI backwards compatibility and failure for unsafe state additions, unreviewed routing/capability alterations, invalid releases and otherwise hidden validator drift.
